## Era I: immutable installation graph
A VIVIM installation is a versioned, immutable directed acyclic graph of exact artifact closures, not a mutable pile of installed files. A family is a compatibility, lifecycle and resource ownership boundary, not necessarily a separate process. Each family can contain many components. A generation root is a single exact mapping of family IDs to verified manifest digests plus configuration schema revision and catalogue digest. Never resolve dependencies during activation. Allow several revisions staged side by side, but exactly one active writer per exclusive resource. Cycles rejected unless explicitly collapsed into one indivisible release family; bootstrap is an externally rooted trust relationship, not an unresolvable package dependency.

Proposed family map (validate against real dependency graph before enforcing):
- F00 recovery/launcher: small native bootstrap and recovery supervisor, stable handoff protocol, local trusted roots.
- F01 Host authority: admission, receipts, resource ownership, data migration coordination.
- F02 native workers: terminal, filesystem, execution and other separately isolated workers; session lifetime pinned to exact generation.
- F03 Studio/Harness: ONE external software actor and browser interaction surface, profile ownership exclusive.
- F04 MCP/provider transport adapters: stable endpoint identity, external client catalogue, version negotiation; no new authority.
- F05 GPUI and phone viewport protocol: same renderer, immutable asset bundles, compatibility-pinned clients.
- F06 intelligence: VLANG, semantic graph, AutoWiki, deterministic execution; partition only if runtime boundaries are real.
- F07 optional capability packages: integrations, models, data-sync workers; namespaced configuration and least privilege.
- F08 local data/config contracts: schema/migration metadata, not mutable user data as a package. Data and secrets live outside immutable store.
Families with real ABI, singleton, schema or resource conflicts must activate in the same transaction. Two unrelated compatible families can stage simultaneously. Atomic commit serializes the global generation root through CAS on the prior generation; a losing transaction must re-resolve. Never hold a global lock for downloads/builds.

Manifest: schema version; family and component ID; release and source provenance; exact digest and byte size; supported platform and architecture; complete path inventory; exact dependency digests; provides/requires contract versions; exclusive resource keys; entrypoint and launch policy; explicit activation mode; migration plan, recovery compatibility; capabilities requested vs previously granted; health checks; minimum bootstrap version; signature and trusted metadata reference. Unknown critical manifest fields fail closed. Validate paths, symlinks/reparse points, case-fold collisions, archives, extraction quotas and signed file inventory. Store per-content digest under local owner-controlled root. No shared writable DLL directories, PATH mutations or arbitrary post-install scripts. Use absolute private loader paths and isolated processes where ABI separation is needed. Prefer physical deduplication only where safe; never hardlink a writable consumer to an immutable blob.

Design reference: Nix immutable closures and generation-based rollbacks (https://nix.dev/manual/nix/2.36/introduction); OSTree atomic deployments (https://ostreedev.github.io/ostree/deployment/); TUF signed metadata, freshness, delegation and anti-mix-and-match (https://theupdateframework.github.io/specification/latest/). Adopt patterns, not dependencies on Linux-only tooling. Trust root and artifact signatures independently verified; local authorized rollback only to known-good, non-revoked artifacts under policy. No unsigned code or privilege expansion via upgrade.

## Era II: recursive self-installation and live activation
User installs or enables a small authorized bootstrap, then optionally connects a supported remote plugin. Plugin can express desired capability family and installation plan, not download/execute untrusted arbitrary code. If no Host exists, browser/cloud plugin cannot silently install native software; offer the signed per-user launcher and explicit OS/user authorization. If Host exists and scoped lifecycle authorization is already granted, install via stable existing endpoint. Bootstrap is never a dependency of itself: it is the trust anchor that installs the first complete graph including a newer bootstrap candidate. A trusted recovery launcher/supervisor can update its alternate slot, verify it and hand over; an independently retained known-good recovery path must remain available. Windows locked executables are not overwritten in place. A/B launcher slots, versioned executable paths, process supervision and verified OS-specific durability; do not claim physical zero downtime for a singleton Host or Windows reboot.

One installation transaction:
1. Resolve requested capability into exact transitive closure against active generation and signed catalogue, including compatibility and resource collisions. Produce human-readable plan and impact: download bytes, disk reserve, permissions changes, restarts, data migrations.
2. Fetch/stage immutable objects with bounded resources; verify signatures, digest, complete closure and platform. No production effects. Reuse existing staging seal.
3. Admit plan through Host policy, explicit approval where privileges, account connections or trust scope increase. Existing authorized same-scope updates may be automatic per user policy. No self-grant. Keep secrets outside manifests and logs.
4. Shadow validation on isolated fixture/read-only production views where appropriate; no duplicate production browser actor or Host writer. Verify readiness and real compatibility. Prepare rollback, retained disk budget and state migration recovery.
5. Compute minimal affected dependency cut from typed contract changes, resource ownership and active session leases; compatible unrelated families untouched.
6. Drain affected admissions; existing jobs remain on their pinned generation until completed or explicitly cancelled. Transfer exclusive resource via durable fencing/lease; incumbent stops writing before successor starts. For compatible non-exclusive services use side-by-side warm candidate.
7. Commit candidate graph root using durable compare-and-swap journal and OS-specific atomic replacement; generation is the only authoritative new-dispatch mapping. New work routes to new version; old leased sessions stay on prior version where compatible. Record exact owner/epoch. Do not assume pointer flip alone is atomic across processes or external systems.
8. Prove readiness, actual harmless capability call, data schema and external discovery, then mark settled. Journal intent/effect/receipt boundaries using existing release journal; incomplete commit reconciles on restart, no blind replay. Affected scope only remains in maintenance when uncertainty exists.
9. On failure, fence candidate, restore compatible previous root/state, verify incumbent service and receipt. If migration cannot reverse, use recoverable snapshot or explicitly require maintenance/forward repair; never overwrite new user data silently. Uninstall is a graph change, reverse dependency check and consented cleanup, not arbitrary directory deletion.
10. Retain prior known-good graph plus active/rollback/session leases; garbage-collect only unreachable digests after retention and disk budget checks. Offer recovery and safe-mode in GPUI.

Activation modes: metadata only; declarative config/capability snapshot; compatible adapter generation; side-by-side worker; session drain/replace; exclusive Host handover; data migration maintenance; launcher slot switch; OS-required reboot. Treat unknown changes as affected, not zero-downtime. Dynamic native code in existing process is not default; stable IPC or WASM sandbox for genuinely appropriate extensions, not raw Rust ABI/dylib replacement.

Concurrency: per-family staging leases, deterministic resource order, one root CAS, per-resource ownership epoch checked at effect boundary, durable idempotency keys, persistent receipts, no global process kill. Two overlapping requests either compose via new compatible resolution or conflict; never silently mix incompatible trees. Active sessions pin exact contracts and artifacts until released. Existing Host remains the sole effect authority; bootstrap recovery cannot execute ordinary user commands or grant privileges. Local developer preview has independent disposable data/profile/endpoint and must not compete for production singleton resources.

## Era III: stable plugin and continuous evolution
Stable MCP endpoint/identity persists across implementation generations. Retain compatible core discovery, status, plan and typed installation lifecycle tools, backed by Host. Capability discovery reflects active graph only. Versioned schemas, compatible aliases, explicit stale catalogue status; do not silently change semantics for existing tool name. MCP list-change notifications when negotiated (https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/server/tools.mdx); compatibility with actual client protocol required. Some clients may cache tools or require explicit refresh; verify client-side discovery and actual invocation, do not claim automatic refresh by sending a notification. Existing Studio actor can perform supported user-authorized plugin settings refresh if necessary. Keep same plugin identity, avoid reinstall/disconnect and no unsupported client bypass. Native installer registration and external service/plugin account consent are separate states.

User journey: Install VIVIM -> select provider/capabilities -> explain additions and permissions -> stage in background within authorized policy -> activate minimal family subset -> discover immediately where supported -> repair/rollback with receipts. No requirement that user learn package managers. GPUI settings centrally control update channel, auto-install scope, bandwidth/disk, update scheduling, maintenance, pause/pin/revert and change history. PWA displays same GPUI state. Runtime capabilities become self-describing for VLANG and AutoWiki via existing registry, not a second graph compiler.

Implementation increments (extensions of existing B07/L+ and not separate parity score):

E02 Rust typed artifact/manifest/lock graph resolver with deterministic closure, conflict witness, SCC rejection and exact manifest provenance.
E03 Rust immutable store and verified staged seal; Windows path and case/reparse checks; low disk and interrupted download handling.
E04 durable generation-root CAS, concurrent transaction leases and journal replay/reconciliation, adapt existing release sequence.
E05 capability impact planner and per-session pinning; integrate current minimum-restart classifier, not a second planner.
E06 stable launcher/recovery A/B and update-the-updater; no in-place overwrite. Real Windows forced termination and reboot/power-loss fault tests.
E07 Host-owned install/upgrade/uninstall/status/repair lifecycle, same-scope automatic policy with local approval for scope expansion.
E08 actual MCP stable endpoint/catalogue lifecycle and Studio refresh integration; client readback.
E09 GPUI settings + receipt timeline, existing config owner; no second renderer.
E10 mutable data schema expand/contract migration, backup and rollback contracts; preserve user data and credentials.
E11 real local acceptance: simultaneous independent updates; shared contract conflict; old session survives adapter update; malicious archive rejected; stale root CAS; candidate crash before/during/after root publication; low disk; interrupted download; stale/revoked signed release; Host singleton fence; launcher upgrade with failed candidate; repeat request idempotency; plugin installs approved dependency without manual shell; cold first install requires supported local bootstrap; no Desktop Commander.
E12 prove two consecutive self-owned upgrades, including updater itself, from actual ChatGPT/VIVIM connection. Record exact source/binary/catalogue/root/receipts, user-data preservation, affected downtime and rollback. No synthetic acceptance.

Priority: E01–E04 first, then one real MCP-adapter family vertical slice E05/E07/E08; then native worker lease preservation, Host handover and updater self-upgrade. Do not decompose all software or replace working release machinery before verifying a narrow vertical slice. Full graph deployment, independent repair and cold bootstrap are proposals, not implemented by this document.
