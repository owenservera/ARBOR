## 1. Implementation order and ownership
P0 A — baseline/recorder lifetime (Harness engineering): instrument existing run and verify observed send -> multiple attributed content events -> terminal content -> durable final -> independent composer readiness. On uncertain timeout, fence dispatch and preserve recorder until bounded reconciliation, not premature run.end; report incomplete if safe finalization cannot be proven. No new send while uncertain.
P0 B — protected incremental delivery (Harness engineering): extend existing recorder/runtime/feed, maintain old snapshot API. Native consumer subscribes using existing authenticated Host route; no polling for supported live deltas.
P1 C — Chrome configuration and adaptive admission: Host supervisor owns approved launch configurations, exact executable and restart. Compare configurations and tab/process topology only after A/B are stable.
P1 D — profiling/overhead: measure guard/reducer/base64/archive and synchronous persistence, optimize individually. Native Rust only where it reduces measured overhead without duplicating authority.
Master integration selects proved changes; Planner registers these as extensions to existing tasks, not a new backlog. Reconcile concurrent claims before editing runtime files.

## 2. Streaming contract (proposed additive wire format)
Existing journal and SSE route remain authoritative/reusable. Extend existing conversation event API with opt-in include=delta (name provisional; verify route query parser), keep include=text compatibility. Use the existing approved transport and authenticated session. Emit:
- conversation.reply_delta: epoch, conversationId, turnId, sourceIdentity (browser epoch, target/session/request and provider message ID when available), eventSequence, baseRevision, operation append|replace, startByte, endByte, text, source, confidence. UTF-8 byte positions on valid scalar boundaries. Append only if prefix exactly matches; provider revisions/non-prefix edits require replace with validated range or reset. No token claim for arbitrary network chunks.
- conversation.reply_reset: snapshot revision, text digest, recovery reference, reason; client fetches authorized full state if replay expired or revision mismatch.
- conversation.reply_terminal: final text digest, durable journal revision, completion evidence, readiness independently reported; not emitted as settled until validated.
Delivery cursors are not durable journal revisions. Bound per-stream replay by events AND bytes, preserve ordering, do not mix target epochs. SSE frames encoded once per event; no repeated full-text hash at each poll. Only hash full canonical text at durable checkpoints/terminal or when necessary to detect replacement. Keep snapshot mode for unsupported adapters.
Where provider adapter already exposes matched protected updates, publish from that validated path; don't expose arbitrary raw recorder chunks or bypass ChunkCredentialGuard. Measure guard holdback separately from local forwarding. Prefer existing reducer event hook; add an ordered internal callback at the earliest protected, attributed, decoded content boundary. Before persistence, events are explicitly provisional; final events only after journal commit. On privacy rejection, invalidate prior provisional state where required and record coverage limits. Never change credential policy for latency.
Race-safe subscribe: register listener with high-water cursor, obtain baseline from journal, replay buffered later events; reject gaps/duplicate sequences. Existing EventFeed slow-client disconnect/reset behavior retained; use conversation GET for recovery. No unbounded queue or blocking CDP socket reader. If queue full, mark gap, stop admission and reconcile from durable state; never silently drop authoritative content.
Native Rust consumer: reuse current Host HTTP/SSE client; parse arbitrary read boundaries, UTF-8 and SSE framing incrementally. One ordered consumer per conversation, bounded Tokio mpsc if already using Tokio. Start test capacity 256 events and 1MiB per worker, 16MiB global (provisional; record peak). Reserve capacity before moving owned payload; cap bytes separately, cancel safely; no spawn per chunk. Keep UI coalescing separate (initial 16–33ms) and no effect on authoritative stream. Offload noncritical disk/export to bounded writer; terminal durability acknowledgement mandatory. Do not promise zero-copy through CDP base64 JSON.

Validate actual executable path, Google Chrome product/version, ownership marker, Chrome process identity and dedicated profile. No silent Edge/Chromium fallback. Preserve security sandbox, site isolation, TLS, updates, auth, cache, service workers and existing required extensions.
Candidate configuration record (data, not current live settings):

- B01 Memory Saver: protect active provider sites via supported user/managed settings; record actual effective setting, not an assumed pref key.
- B02 Energy Saver: off on dedicated test fleet; record power source; benchmark plugged-in.
- B03 --disable-background-timer-throttling
- B04 --disable-renderer-backgrounding
- B05 --disable-backgrounding-occluded-windows
- B06 remove only nonessential extensions/sync/speculative preload/notifications via supported settings; test separately.
- B07 GPU default vs disabled only if measured workload warrants; B08 normal vs Above Normal Windows priority only if CPU contention warrants; no realtime priority.
- B09 optional selective unnecessary media/image blocking, provider compatibility test before use; no blind request interception or API changes.
- B10 single profile/multi-tab vs isolated profiles (distinct existing authorized sessions, no cookie copying).
Each candidate individually compared with baseline under identical provider/model/response class and alternating order; no blanket flag recipe. Use chrome://version and supported settings plus read-only process inventory to verify effective config. CLI flag support varies; treat as ineffective if no observed behavioral change. Never fake visibility, play silent audio, or force periodic tab activation merely to defeat scheduling.
Active workers: READY_EMPTY -> DISPATCHING -> OBSERVED -> STREAMING -> CONTENT_TERMINAL -> SETTLED_READY. DRAFT_PRESENT, UNCERTAIN, RECOVERING, FROZEN/DISCARDED or stale epoch fence dispatch; preserve pending state. Idle means no unresolved work/draft and verified readiness, not simply low CPU.
Initial admission starts at 1 then 2,4,6,8 only on healthy host. Provisional stop-escalation signals: sustained system CPU >85%, available RAM <3 GiB, commit >85%, sustained paging, increasing queue backlog, repeated lifecycle/transport errors or provider limit. Sample at 1s; evaluate rolling 30s and hysteresis (e.g. 60s healthy before increase). These are experiment defaults, not automatic production policy. Never cancel active sends to free resources. Current hardware assumptions must be confirmed at baseline.
